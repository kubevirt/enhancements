## Overview

Propose `kubevirt.io/display-name` as a **provisional, optional label** on a VirtualMachine's top-level `metadata.labels`. It holds one mutable, human-readable inventory name. A reader presents its nonempty value when present and otherwise presents `metadata.name`. There is no blanket defaulting or backfill. Customers who want display-name search populate this label alongside `metadata.name` through CLI, GitOps manifests, or the UI. Users may set the label. For VMs outside GitOps management, the naming service writes it only to suffix a conflicting new VM, restore that VM's recorded assignment after a lifecycle update, or roll back a raced explicit edit. Git owns labels on GitOps-managed VMs: the service never adds, changes, removes, or rolls back their display-name label; unresolved conflicts raise an alert for correction in Git. The key and its community ownership require agreement before implementation as a supported convention.

Changing this label changes presentation and inventory discovery, not Kubernetes identity or VM runtime configuration. The proposed delivery scope is **HCO-managed installations**, with a dedicated naming service deployed by HCO as an operand. A separate naming operator is not required. Clone, restore, and VM pool APIs and controllers remain unchanged. The naming service reconciles resulting VM create/update events; optional name prompts and assignment presentation belong to the UI. Supported-version tests must verify this separation. When enabled, the default policy detects namespace-scoped effective-name conflicts, including resource-name fallbacks, and automatically repairs eligible VMs outside GitOps management; customers can explicitly opt out. GitOps conflicts require source correction and are excluded from automatic convergence guarantees. A successful direct create is initially provisional: a duplicate can be stored and visible until eligible automatic repair completes or a GitOps owner resolves it in Git. This is a conflict-management contract with conditional eventual repair, not a pre-persistence or unconditional namespace-uniqueness guarantee. Standalone KubeVirt has no managed display-name uniqueness from this proposal.

## Motivation

Administrators need to update inventory names when an organization changes its naming convention, retain or align a source platform's inventory name during migration, and remedy customer naming-policy violations without replacing a VM. Product accepts Kubernetes label-value conventions for inventory names. An import UI offering a display name maps unsupported source text to a valid value for user approval; leaving the label unset remains supported. Console presentation, editing, and discovery, together with existing `oc`/`kubectl` label workflows, address those inventory tasks while automation continues to use stable Kubernetes identity.

This is a partial answer to a full-rename RFE. It does **not** rename literal `metadata.name`, Pods, DataVolumes, PVCs, Secrets, or ConfigMaps. A customer policy that inspects those literal resource names remains unmet; the remaining RFE requirements need customer validation. No regulation is assumed to mandate a particular VM-name pattern.

KubeVirt previously removed object rename after a reported data-loss case involving `dataVolumeTemplates` ([kubevirt/kubevirt#5564](https://github.com/kubevirt/kubevirt/pull/5564)). The lesson for this proposal is to preserve object identity, not to assume every inventory integration already understands a display name.

## Goals

- Set, change, and clear an inventory name on running or stopped VMs without a naming-induced guest restart, VMI recreation, or migration.
- Give presentation, uniqueness, monitoring, and integrations one effective-name rule, while CLI and UI display-name search use the populated label and ordinary resource-name lookup uses `metadata.name`. Keep namespace, `metadata.name`, and UID available for identification.
- Expose the effective name as a `display_name` label on `kubevirt_vm_info` through `kubevirt-observability-controller`, retaining canonical monitoring identity.
- Keep existing VMs readable without blanket defaulting, backfill, or mass writes; automatically label only eligible new VMs needing collision repair. Preserve Git ownership on GitOps-managed VMs and alert on unresolved conflicts.
- Document lifecycle behavior for create, pool scale and update, clone, restore, import, migration, delete, backup, and policy transitions.
- Deliver default namespace-scoped conflict detection, automatic repair for eligible VMs outside GitOps management, alerts and source remediation for GitOps conflicts, an explicit customer opt-out, and safe activation for existing deployments.

## Restrictions

- In an HCO-managed installation with the feature enabled, duplicate effective names within one namespace may persist briefly during reconciliation, remain during a visible activation-pending state, await correction in Git for GitOps-managed VMs, or remain under an explicit `Disabled` opt-out. If the naming service is unavailable, convergence is delayed and the product must show the unresolved state. Standalone KubeVirt has no managed rule. Every discovery result and destructive confirmation must expose canonical identity; a consumer must never silently choose the first match.
- The displayed name is not an API object identifier, authorization key, or positional operand to existing `virtctl start`, `stop`, and similar commands. Native label selectors can discover VMs by the stored value, but supported integrations must use stable labels for controller ownership and policy dependencies. Discovery resolves a canonical namespace/name/UID before any action.
- The label supports native exact and set-based selection of populated values. Display-name lookup requires a nonempty label; absence or an empty value contributes no display-name search match. Combined resource/display-name search also checks `metadata.name`; server-side prefix, subsequence, and regex matching are not provided by label selectors. Discovery needs authorized list access.
- The default policy repairs eligible conflicts after VM persistence, including creation without a label. Known conflicts on explicit user edits and clears are rejected for all VMs; lifecycle metadata propagation follows the separate post-update reconciliation contract. A race missed by validation is rolled back only outside GitOps management; GitOps-managed VMs retain the value from Git and raise a conflict alert. A successful API write does not mean its requested effective name has settled.

## Non Goals

- Literal Kubernetes object rename or automatic renaming of related resources, guest hostname, MAC/IP configuration, Service selectors, or runtime configuration.
- Changes to clone, restore, or VM pool controllers, their APIs, or completion status for display-name handling. These controllers do not wait for naming settlement.
- Implicit command resolution by display string. Display-name lookup uses an explicit label selector or UI filter, separate from ordinary resource-name operands.
- Using `kubevirt_vm_info` as proof of naming settlement or Events as durable audit history. GitOps conflict alerting is required delivery work, with authoritative naming status and a documented remediation policy.
- A new search service, persistent full browser VM cache, or regex search backend without measured need.

## Definition of Users

- VM administrators editing names and resolving ambiguous inventory entries.
- Migration administrators mapping source inventory names to supported display names.
- CLI and GitOps users who need predictable discovery and field ownership.
- Console, importer, backup, monitoring, and other integration developers.
- Cluster administrators resolving existing conflicts, activating default reconciliation, or choosing an explicit opt-out.

## User Stories

- As an administrator, I can display `SAP-Database-Server` for `production/finance-vm-001`, then change or clear it without changing the running guest.
- As an importer, I can map a source inventory name to a valid requested display name and see the final assigned name if a collision requires a suffix.
- As a CLI or UI user, I can populate the display-name label alongside `metadata.name`, search by its value, see every match with namespace/name/UID, and act on a selected canonical target. Resource-name lookup remains available when the label is unset.
- As a cluster administrator, I can identify and resolve legacy conflicts before default reconciliation activates, or explicitly opt out, without silently renaming existing VMs.
- As a GitOps owner, I retain label ownership in Git, receive an alert for a persisted naming conflict, and resolve it by changing Git; the naming service never rewrites my VM's display-name label.

## Design

### Terminology and placement

These are proposed product terms, not universal Kubernetes definitions:

| Term | Intended meaning | Choice here |
| --- | --- | --- |
| Display name | One mutable, human-readable inventory name; presentation falls back to the resource name | Use for the proposed label contract. |
| Alias | An alternative address, potentially one of several | Reserve for a separately specified command-resolution feature; label selection here discovers inventory. |

A display name may be searchable and unique within its namespace without becoming Kubernetes identity. The label belongs to the **VirtualMachine top-level `metadata.labels`**, not `spec.template.metadata`. It uses Kubernetes's existing [label mechanism](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/) for mutable inventory presentation and native selection of stored values, with no dedicated CRD schema field. Product accepts the label-value syntax and length limits. Standardizing the key and its ownership still requires community review.

### Customer workflow for display-name search

Customers keep `metadata.name` as the canonical resource name. To search by a display name, they also populate a nonempty `metadata.labels["kubevirt.io/display-name"]`:

- **CLI:** Set the label with `oc label` or `kubectl label`, then discover matching VMs with an explicit label selector. Inspect all matching canonical identities and use the selected namespace/resource name for actions.
- **GitOps:** Declare both `metadata.name` and the display-name label in the VM manifest. For existing VMs, add the label to their source manifests in Git and synchronize them to populate the live VM labels before using native label-selector search. Keep the label in Git for subsequent reconciliations; a live-only label edit is not the supported GitOps workflow. Declare GitOps ownership before the first naming reconciliation. Resolve conflict alerts by changing the label in Git; the naming service does not rewrite it.
- **UI:** Enter a display name in the creation or edit form. The form writes the same top-level label; display-name search uses that populated value.

The label may equal `metadata.name` when that text meets label-value conventions, but no component automatically copies the resource name into it for search. Without a nonempty label, the UI still presents `metadata.name`, and customers can search by resource name. An explicit display-name filter returns only populated label values. A settled clear removes that display-name search entry and restores resource-name presentation. Documentation and UI help must explain this opt-in consistently, including for existing VMs.

### Effective-name and validation contract

For a VM, `effectiveName = nonempty(metadata.labels["kubevirt.io/display-name"]) ? label : metadata.name`. Absence is normal. A clear/reset operation removes the key; it does not store the resource name. Readers also treat an explicit empty value submitted by a direct client as unset. Supported writers remove the key for an empty edit. Neither the key nor its value is copied into VMI template metadata by this convention.

A **nonempty stored value** follows [Kubernetes label-value syntax](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/#syntax-and-character-set): 1–63 ASCII characters, beginning and ending with an alphanumeric character (`A–Z`, `a–z`, `0–9`), with alphanumerics, hyphens (`-`), underscores (`_`), and dots (`.`) inside. Spaces, Unicode, slashes, and other punctuation are not accepted. Kubernetes permits an empty label value; supported writers instead remove the key for an empty edit, and readers treat a direct client's explicit empty value as unset. Kubernetes API validation enforces label syntax and length for direct writes even when the naming service is disabled. UI and CLI writers that offer this label must apply the same rules and report actionable errors. They must not silently trim, lowercase, or rewrite an explicit edit.

Uniqueness uses **exact, case-sensitive string equality**, consistent with exact label selection. `SAP-DB` and `sap-db` are distinct effective names; case-insensitive UI discovery can return both. No Unicode normalization is needed for stored values. Fallback `metadata.name` retains its existing API constraints and may exceed 63 characters; the label limit does not shorten or invalidate a VM's resource-name fallback. A fallback longer than 63 characters cannot equal a stored display-label value and remains unchanged; it is not copied into a label. Such a VM remains searchable by resource name; customers choose a valid label value if they also want display-name search. Collision repair for eligible names must keep the assigned label within 63 characters using the suffix rule below.

An import UI that offers source-name mapping must show the mapping to a valid requested label value for user approval, for example `SAP Database Server` to `SAP-Database-Server`. Product and UI owners define this optional conversion and user-acceptance workflow; backend import completion does not depend on naming settlement, and different source names may map to the same requested value and still need collision repair. The naming service validates known conflicts on explicit user set/change/clear, including direct API writes; lifecycle-controller metadata propagation follows the post-update reconciliation contract. Labels do not provide cross-object uniqueness; validation alone cannot prevent concurrent conflicts. The reconciliation contract below handles races and outages.

| Approach | Benefit | Cost |
| --- | --- | --- |
| Populate label from resource name | Label-only consumers can query populated values. | Resource names longer than 63 characters cannot be copied verbatim; blanket writes, duplicate storage, ambiguous clear semantics, and source-name inheritance on clone. |
| Optional label with read-time fallback **(proposed)** | Existing VMs remain readable without blanket writes; customers populate the label to opt into display-name search. | Presentation and conflict detection implement fallback; eligible new conflicts are repaired outside GitOps management, while GitOps conflicts require source remediation. Known conflicting clears reject; raced clears roll back only outside GitOps management. |

Fallback can collide with an explicit name: VM `sap-db` has no display label; VM `vm-002` has label `sap-db`; both would display as `sap-db`. The default policy observes both after creation, retains the settled holder, and adds a suffix to an eligible newer VM outside GitOps management. If repair would require changing a GitOps-managed VM, it preserves that label and raises a conflict alert instead. Thus even a new VM created without the key can gain one **only** to repair a collision. The scope is **effective names**, not merely nonempty label values. Create without a key, clear, recreation, and activation all participate. A known conflicting clear is rejected and leaves the label in place; a concurrent clear that slips through validation is rolled back to its last settled label only outside GitOps management; a GitOps-managed conflict is reported for correction in Git. Suffixing a clear would defeat the requested absence.

Resource names and effective names occupy distinct lookup modes. For example, VM `sap-db` may have display label `Production-DB`, while VM `vm-002` has display label `sap-db`. Their effective names differ, so both remain allowed after convergence. Ordinary CLI operand `sap-db` identifies the first VM by `metadata.name`; explicit display-name lookup for `sap-db` identifies the second. A combined inventory search returns both with namespace/name/UID and the matched field. Populating labels on every VM would **not** remove this cross-mode search ambiguity. Preventing it would require reserving display names against every other VM's resource name even when that other VM has a different effective name. That stronger restriction is not proposed.

### Existing behavior used as design evidence

At inspected `kubevirt-plugin` main revision [`e77daba`](https://github.com/kubevirt-ui/kubevirt-plugin/commit/e77daba9b08fd46f25091f3747113a19befe3899), the [description editor](https://github.com/kubevirt-ui/kubevirt-plugin/blob/e77daba9b08fd46f25091f3747113a19befe3899/src/utils/components/DescriptionItem/components/DescriptionItemDescription.tsx) writes nonempty input and deletes the key on empty input. The [VM description filter](https://github.com/kubevirt-ui/kubevirt-plugin/blob/e77daba9b08fd46f25091f3747113a19befe3899/src/views/virtualmachines/list/filters/getDescriptionFilter.ts) calls `fuzzyCaseInsensitive`, which lowercases both strings and calls [`fuzzysearch`](https://github.com/bevacqua/fuzzysearch/blob/master/index.js). That algorithm matches the search characters in order, including non-contiguous matches; it is neither regex nor substring-only matching. The [VM list](https://github.com/kubevirt-ui/kubevirt-plugin/blob/e77daba9b08fd46f25091f3747113a19befe3899/src/views/virtualmachines/list/VirtualMachinesList.tsx) filters watched resources before local pagination; its [data source](https://github.com/kubevirt-ui/kubevirt-plugin/blob/e77daba9b08fd46f25091f3747113a19befe3899/src/views/virtualmachines/list/hooks/useVMDataSource.ts) and [resource hook](https://github.com/kubevirt-ui/kubevirt-plugin/blob/e77daba9b08fd46f25091f3747113a19befe3899/src/views/virtualmachines/search/hooks/useAccessibleResources.ts) use cluster-wide or per-namespace watches and a 10,000-object fetch limit on some paths. That code does not prove a complete inventory search or server-side prefix autocomplete at all scales.

At inspected `kubevirt` revision [`c418f32`](https://github.com/kubevirt/kubevirt/commit/c418f32d6fefd864f19d3a7f436dd6bfa8827036), [clone patch generation](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-controller/watch/clone/vm-target.go) supports top-level `labelFilters`. [Restore](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/storage/snapshot/restore.go) copies snapshot top-level labels when creating a missing target; for an existing target it deep-copies that target, replaces its spec, and retains its top-level labels. `spec.patches` apply only to new-target VM creation in this implementation. These are compatibility observations, not requirements to add lifecycle-specific naming logic. The naming service observes the resulting VM; the UI may use existing API options when offering an explicit name.

At the same `kubevirt` revision, the VM pool controller [copies template labels into each new child VM](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-controller/watch/pool/pool.go#L948-L950) and [replaces them on child updates](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-controller/watch/pool/pool.go#L1085-L1087). A static template label can therefore create duplicate child names or overwrite/remove a naming-service assignment on an update. Running after creation addresses the initial copy; later updates also require reconciliation. The naming service handles those VM events without changing pool templates or controller logic. Pool [ownership selection](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-controller/watch/pool/pool.go#L1544-L1585) uses child labels, so the service must not mutate this key when doing so could change membership. The [outdated-VM check](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-controller/watch/pool/pool.go#L1306-L1334) compares the recorded pool-template revision with the current template; it does not compare the child's display-name label with the template value. A display-name-only repair that preserves pool revision labels should therefore not trigger another template application. The supported-release compatibility requirement is safe repair after a genuine pool template update, not resolution of a presumed continuous controller write loop.

### Console and discovery contract

VM list rows, detail headers, topology, related-resource associations, and success/failure messages show the current effective name with canonical namespace/resource name accessible. Related-resource views can show their association with the renamed VM without copying its display string onto every resource. Creation, clone, restore, and rename dialogs distinguish requested text, provisional effective text, settled assigned text, and resource identity. Destructive confirmations include namespace/name and, where available, UID. Set/change/clear preserve unrelated metadata. A visible naming condition reports provisional, conflict, settled, and unavailable states; a successful VM API response alone does not establish that the displayed name is settled.

Combined inventory search checks both `metadata.name` and the nonempty stored display-name label, and identifies the field that matched. A VM without a nonempty label can match the resource-name field only; presentation fallback is not a synthetic display-name search value. The proposed normal partial mode follows the verified description filter: case-insensitive ordered-character (subsequence) matching. Exact matching is also available for CLI lookup. Partial discovery is case-insensitive, while exact display-name lookup and uniqueness use case-sensitive equality. Zero matches report no result; one match returns its canonical identity; many return all matches and require explicit selection. Exact display-label lookup can also return several VMs while a conflict is unresolved. Even after convergence, combined search can return both VMs in the cross-mode example above. Never choose the first match. Bound autocomplete suggestions, while a separately accessible filtered result path must cover the complete selected, authorized inventory. Reuse the existing watch/list path where feasible, measure its limits, and do not equate current-page filtering or a 10,000-object limit with complete inventory search.

### CLI, API, and GitOps

Ordinary direct VM create remains supported. The following direct edits are also supported when the HCO naming service is active: validation rejects a known conflict or an edit on a VM whose initial assignment is pending, and a racing conflict is rolled back after persistence only outside GitOps management. GitOps corrections that remove a conflict must remain admissible even while the VM is conflicted. The caller must read the naming condition to distinguish API acceptance from settlement:

```bash
oc label vm finance-vm-001 -n production \
  kubevirt.io/display-name='SAP-Database-Server' --overwrite
oc label vm finance-vm-001 -n production kubevirt.io/display-name-
```

Existing `oc`/`kubectl` commands provide the CLI workflow; no external CLI plugin or new `virtctl` command is required. Use an explicit label selector for exact display-name lookup, inspect all returned namespace/name/UID identities, and pass the selected canonical namespace/resource name to subsequent commands. Ordinary action operands continue to resolve **only** `metadata.name`. A label query matches nonempty stored values and never adds resource-name fallback candidates. Customers populate the label through CLI, GitOps, or UI before querying it. Canonical resource-name lookup remains available independently.

Exact label lookup can return multiple matches during reconciliation, in `Disabled`, or without HCO. Customers must inspect the results and select a canonical target rather than automatically taking the first result or acting on every match. Scripts must explicitly handle zero/one/many results and recheck UID or resource version where the target API supports it; this proposal adds no atomic lookup-and-action guarantee to existing commands. Read the naming service's external status with ordinary API-resource commands to distinguish provisional names, conflicts, rollback, and settlement; documenting that resource and commands is required when its API is defined. Namespace scope and list RBAC remain explicit: label-selector LIST does not grant access where only named GET is authorized. Kubernetes [label selectors](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/#label-selectors) provide equality and set membership, without prefix, subsequence, or regex matching. [Field selectors](https://kubernetes.io/docs/concepts/overview/working-with-objects/field-selectors/) do not select this metadata label. Combined and partial inventory search are console requirements; additional CLI search commands are outside the delivery scope.

Native selection of **stored display-label values** is available directly. This command returns canonical identities for all selected VMs; it does not include resource-name fallbacks:

```bash
oc get vm -n production -l 'kubevirt.io/display-name=SAP-Database-Server' \
  -o custom-columns='NAMESPACE:.metadata.namespace,NAME:.metadata.name,UID:.metadata.uid'
```

For customers who need combined CLI discovery, this optional pipeline illustrates **combined exact, case-sensitive discovery within one authorized namespace**. It searches resource names and populated display labels, presents the effective name, and returns every match rather than selecting one:

```bash
oc get vm -n production -o json |
  jq -r --arg query 'SAP-Database-Server' '
    .items[]
    | (.metadata.labels["kubevirt.io/display-name"] // "") as $stored
    | (if $stored == "" then .metadata.name else $stored end) as $display
    | select(.metadata.name == $query or ($stored != "" and $stored == $query))
    | [.metadata.namespace, .metadata.name, .metadata.uid, $display]
    | @tsv
  '
```

The pipeline lists candidates only. It does not perform an action, label the matched field, inspect naming status, or provide partial or cross-namespace search. Inspect every result and select a canonical target separately; it must not be piped into an automatic first-match action.

### GitOps ownership and conflict remediation

Git is the source of truth for labels on a GitOps-managed VM, including an absent or empty display-name label. Customers declare the optional label alongside `metadata.name` when they want display-name search. The naming service must never add, change, remove, suffix, or roll back that key on these VMs. The service may write its own external naming status. A VM produced by a GitOps-managed lifecycle resource must be classified before any repair; classification cannot depend on modifying that controller. No separate naming request, field relinquishment, or automatic write-back to Git is required. Console direct-edit flows and CLI documentation direct these customers to update Git. For existing VMs, customer guidance must explain how to add the label in Git, synchronize it onto the VM, verify the stored value, and then use native label selectors or explicit display-name lookup. Resource-name fallback alone does not populate a label or make a VM match a display-name selector. Customers choose valid, nonconflicting values; the naming service performs no automatic backfill.

The supported GitOps integration must declare source ownership at creation, before the first naming reconciliation, through an agreed VM metadata marker or namespace policy. The exact marker/configuration API requires agreement before delivery; do not assume every GitOps tool sets the same tracking metadata. `managedFields`, a field-manager string, or a GitOps application label alone is not a universal detection contract. Classification must cover an absent display-name key, clone/restore/import targets, namespace-policy changes, and adoption of an existing VM by GitOps. If ownership cannot be established or is ambiguous, suppress automatic label writes and report the classification problem. Recheck current ownership before every conditional repair or rollback, cancel queued writes after adoption, and test ownership transitions against concurrent writes before claiming protection. A supported integration that cannot establish ownership before mutation blocks delivery for that workflow.

Known conflicting set/change/clear requests still reject with an actionable validation error, including GitOps syncs. A newly created GitOps VM or a raced edit/clear can persist a duplicate: preserve its label, report `Conflict` with reason `GitOpsRemediationRequired`, and raise the conflict alert described below. Every GitOps-managed VM observed in a duplicate effective-name group must have conflict status and be covered by alerting, whether it is new or existing, the settled holder or a competing VM, and whether its peers are GitOps-managed or eligible for automatic repair. A held assignment does not justify hiding an observed duplicate; the alert evaluation delay can filter short repair transients. Do not suffix an existing unrelated VM to make room. Two conflicting GitOps VMs remain conflicted until their source declarations are corrected. A correct GitOps sync may succeed while a persisted naming conflict remains; API/sync success is not naming settlement.

The alert identifies the affected namespace/name/UID and links to current UI/CLI naming status listing all conflicting canonical targets. They tell the owner to choose a different valid label in Git, synchronize it, then verify current conflict-free status. A rejected edit leaves the live value unchanged and must be visible in the sync error; the persisted-conflict alert alone cannot detect a request that never stored. A correction to a nonconflicting value must be allowed from `Conflict` without waiting for prior settlement. Once the updated object is observed and no conflict remains, report `Settled` and clear the conflict signal. Historical Git values must not remain permanently reserved after source changes. A suggested numeric suffix is advisory and can become occupied before synchronization; revalidate it. Dry-run validates current input but cannot reserve a name.

### Monitoring contract

Add a `display_name` label to the existing `kubevirt_vm_info` gauge in **`kubevirt/kubevirt-observability-controller`**. Its value is the VM's effective name: the nonempty top-level `metadata.labels["kubevirt.io/display-name"]`, otherwise `metadata.name`. Absence, an explicit empty value, or a clear therefore reports the resource name. Read from VM metadata, not VMI-template labels. The collector reports the latest observed value, including a repair suffix or rolled-back edit; the naming condition remains the source of settlement and availability status.

The observability-controller already [watches KubeVirt resources and exposes their metrics](https://github.com/kubevirt/kubevirt-observability-controller#overview), with its own [`kubevirt_vm_info` collector](https://github.com/kubevirt/kubevirt-observability-controller/blob/main/pkg/monitoring/metrics/vmstats_collector.go). Add the label, collector tests, and metric documentation there. This requires companion observability-controller work, with no planned change to `kubevirt/kubevirt` or `kubevirt/api`. Deployments still using the legacy KubeVirt exporter need the supported observability-controller migration before this metric requirement is met; this proposal does not require a legacy-exporter backport. Define the supported exporter version and scrape ownership so old and new sources do not double-count VMs during rollout.

Keep `name` and `namespace` as canonical metric labels and join keys; preserve other existing identity labels where the deployed exporter provides them. Use `display_name` for inventory presentation, not alert identity or cross-metric joins. The label follows the same fallback rule whenever the updated collector runs, including standalone KubeVirt, HCO gate-off, and `Disabled` policy, without implying managed uniqueness. Do not add it to every VM/VMI metric.

A name change creates a new Prometheus label set. The previous series stops receiving samples while retained historical samples keep the old text. Emit one current `kubevirt_vm_info` sample per VM and measure series churn from edits and suffix assignment. Audit observability-controller rules, dashboards, HCO integrations, and remote-write consumers for implicit full-label matching, aggregation, time-window queries, and display-text exposure. Verify rename and clear behavior without changing counts, joins, alert identity, or alert duration. During mixed-version rollout, consumers must tolerate an absent `display_name` label and fall back to canonical text.

GitOps conflict alerting is required alongside the inventory metric. The naming service publishes an authoritative per-VM conflict signal from fresh reconciliation state, with canonical namespace/name/UID identity and bounded reason values, including `GitOpsRemediationRequired`. HCO installs its scrape configuration, a warning alert (provisional name `VMDisplayNameConflict`), and a runbook. Preserve the affected VM's namespace in the alert. Keep mutable display text and the list of conflicting peers in status and alert details rather than alert identity. Define the rule's evaluation delay, status freshness bound, severity, cardinality budget, and availability alert before release. A persistent GitOps conflict must remain visible and firing until verified source remediation, VM deletion, or an explicit policy disablement; stale/missing metrics or a controller outage must not be presented as successful remediation. Availability monitoring must cover a lost conflict signal. Events may supplement status and alerts but do not replace either. Test alert firing, retention, resolution, and outage/restart behavior; `kubevirt_vm_info` alone cannot establish source ownership or settlement.

### Default conflict policy and eventual repair

Proposed policy modes are `AutoResolve` (default), `Warn` (transition only), and `Disabled` (explicit customer opt-out); these names and the policy API are illustrative. The scope is one namespace and the equivalence rule applies to **effective names**, whether the label is present or absent. `AutoResolve` accepts direct VM creation, then repairs an eligible conflicting new VM outside GitOps management by writing a unique display label. GitOps-managed VMs use detection, alerting, and source remediation within the same policy; they do not receive repair writes. It rejects a **known** conflict on explicit set/change/clear; validation is advisory against races, which the reconciler must repair outside GitOps management or report for GitOps remediation. `Disabled` accepts duplicates without repair and must be a deliberate, visible choice. `Warn` inventories and reports legacy conflicts without renaming; it is not a silent permanent default or a uniqueness guarantee.

The proposed guarantee is **eventual automatic repair for eligible VMs, with source remediation for GitOps conflicts**. With `AutoResolve` active, activation complete, the naming service healthy and able to reconcile, conflicting writes quiescent, and no conflict requiring a Git-owned label change or another protected write, effective names converge to unique values. A namespace containing an unresolved GitOps conflict has no unconditional convergence guarantee, even with a healthy controller: it remains visibly conflicted and alerting until its owner corrects Git. Temporary duplicates may exist after creation or concurrent updates, and an outage delays convergence. Pending conflicts and unavailable or stale settlement status must remain visible; clients continue to identify action targets by namespace/name/UID. This is a design contract whose convergence, failure recovery, and repair-time and availability targets must be demonstrated by implementation testing before release.

This approach is consistent with the [Kubernetes controller model](https://kubernetes.io/docs/concepts/architecture/controller/), in which controllers observe current state and reconcile it toward desired state. The comparison describes the architecture; [Kubernetes labels do not provide uniqueness](https://kubernetes.io/docs/concepts/overview/working-with-objects/labels/#label-selectors). Kubernetes [resource-name uniqueness](https://kubernetes.io/docs/concepts/overview/working-with-objects/names/) is an API-enforced identity constraint, while this proposal adds a separate, eventual policy for display text. Following the controller pattern alone does not prove convergence: stable assignments, collision retries, outage recovery, protection of Git-owned labels, GitOps alert/remediation behavior, and safe repair after VM pool template updates remain required delivery evidence.

New HCO-managed deployments with the HCO feature gate active start in `AutoResolve`. Existing deployments enter a visible activation-pending state. The service records a namespace inventory boundary, inventories every VM's effective name and GitOps ownership, invalid legacy values, VM pool templates, and ownership selectors, and reports conflicts with namespace/name/UID. Administrators resolve conflicts among VMs present at that boundary or explicitly opt out; activation does not silently rename those legacy VMs. Creates during the pending transition remain visible as provisional and must be included in the final inventory. Once active, the resolver may suffix an eligible conflicting VM outside GitOps management created after the boundary, even if its create preceded activation. Git-owned conflicts are reported and alerted for source remediation. Unlike strict pre-persistence enforcement, no scan/write admission fence or precreate claims are required: the active reconciler also observes writes after activation. Pending status must not claim uniqueness, and an interrupted scan resumes safely with the same protected legacy set or restarts a clearly reported inventory. Unrelated updates to legacy VMs must not be rejected solely because an unchanged value predates validation. There is no blanket label backfill.

The naming service observes persisted VMs and maintains durable, UID-bound settled assignment state (including the last accepted label or absence), separate from a requested base name. It records the base request before overwriting a new VM's label, so a restart does not lose intent. A VM without current settled state is `Pending` or `Unknown`, including immediately after successful direct create and during service outage. A condition surface available to UI and CLI reports the canonical VM identity, requested/current/assigned effective names, last observed VM version, and `Pending`, `Conflict`, `Settled`, or `Unavailable`; a stale condition must never be presented as current. The exact API is open. When several VMs request an equivalent name, an existing settled holder retains it; if none is settled, the controller chooses a winner deterministically by creation timestamp then UID.

For a losing **new** VM eligible for automatic repair outside GitOps management, try readable candidates in order: `<base>-1`, `<base>-2`, `<base>-3`, and so on. For example, after `sap-db` is taken, assign `sap-db-1`; if that is taken too, try `sap-db-2`. Select the first available candidate by checking its complete value against every other effective name, including resource-name fallbacks, and held settled assignments using exact case-sensitive equality. Persist the assigned value in durable state bound to the VM UID. Concurrent attempts may select the same candidate: deterministic winner selection and collision retries must resolve that race before reporting settlement. The sequence is a naming convention, not an atomic uniqueness guarantee.

Reserve room within the 63-character label limit for the hyphen and a positive decimal integer starting at 1, shortening the original requested base prefix as needed. The retained prefix must remain nonempty and begin and end with an alphanumeric character. Recheck the complete candidate after shortening, including when a larger number needs more digits. Only collision repair may shorten this new VM's base; the full request remains in assignment state. Always derive candidates from that recorded request, not from a previously assigned suffix. Treat a user-supplied numeric ending as part of the requested base: a conflict on `sap-db-1` tries `sap-db-1-1`, not `sap-db-2`. Each retry must stay within label syntax and length limits.

Assignments remain stable across reconciliations and restarts. Deleting an earlier VM does not rename or renumber surviving VMs; a later new VM may reuse an available candidate. Reconciliation writes use resource-version preconditions and are idempotent across retries; delete/recreate creates a different UID and a new assignment. The service must never relabel an unrelated existing VM to make room. These automatic assignments apply only outside GitOps management; Git-owned labels are protected by the source-ownership contract above.

For an explicit edit or clear, validation rejects known conflicts and rejects edits while that VM's initial assignment is pending. A nonconflicting GitOps correction from `Conflict` is allowed. The following automatic rollback protocol applies only outside GitOps management; raced GitOps conflicts preserve the submitted value and raise an alert. The last settled name remains held by that UID until its edit settles or rolls back; a new VM requesting that name waits for the outcome before final assignment. If concurrent writes pass validation and collide, the service rolls the losing edit or clear back to its durable last settled label using a conditional update; it does **not** silently suffix that edit. It reports the rejected/rolled-back intent and preserves unrelated VM changes. A newer edit wins only after its own current value is re-evaluated; stale rollback may not overwrite it. If rollback cannot complete, status remains visibly conflicted and automatic convergence is not yet achieved. An API success can therefore be followed by a visible rollback. This behavior, including recovery after a controller outage, needs a tested failure and status contract.

Automatic suffixing applies by default to eligible **new VM creation outside GitOps management**, including VMs produced by clone, import, new-target restore, or pool controllers. The naming service reacts after the VM is persisted, independently of the originating operation's completion. It does not change lifecycle requests, templates, or their status. A creation without the label normally keeps it absent; an eligible conflicting fallback gains the repair label. UI flows may ask for a valid name or suggest one before submission, and show the naming service's provisional/settled status afterward. These checks improve the experience but cannot reserve a name or replace reconciliation. GitOps-owned values and absence remain protected on every path.

### Reconciliation after lifecycle operations

The naming service watches resulting VM create/update events and maintains stable assignments by VM UID, regardless of which controller produced the VM. Clone/restore controllers and the pool controller continue their existing work without calling the naming service or waiting for it. Their successful completion does not imply display-name uniqueness. The UI obtains naming status separately; CLI and GitOps users can inspect the same external status and alerts. A restore over an existing VM is an update to the same UID, not a new creation eligible for a fresh automatic suffix.

A later pool template update can overwrite or remove a service-assigned label on its child VMs. For a VM outside GitOps management with a recorded repair assignment, the naming service must recognize that update and conditionally restore the same assignment once it is still safe and available, rather than allocating another suffix on every update. It must distinguish lifecycle metadata propagation from an explicit user set/change/clear, which retains the edit-validation and raced-rollback contract. Trustworthy classification, rechecking current ownership and resource version, and recovery across restarts are implementation requirements inside the naming service. An owner reference alone does not prove who made an individual edit. Naming admission must not reject an existing lifecycle controller's reconciliation solely because it reapplied an inherited display name; test this distinction without adding lifecycle-controller code. Ambiguous updates remain visible and unmodified until safely classified.

Pool ownership selectors must use stable identity labels. Before mutating a pool child, the naming service checks the owning pool's `matchLabels` and every `matchExpressions` operator through read-only observation. If the display-name key participates in membership, or ownership cannot be established, suppress the label write and report an actionable conflict, with an alert for a persistent unsafe naming state. UI pool forms can flag that usage and suggest a separate stable selector. The naming service does not rewrite the pool, add admission requirements to pool create/update, or alter membership to make a name unique. Activation reports existing unsafe uses for administrator remediation.

The expected pool sequence is a template update, the pool controller's child update, then naming-service repair of any overwritten assignment. The naming service preserves pool revision and unrelated labels, so its repair should not itself make the child outdated. Compatibility tests must verify stable settlement after the template update and that changing only the display-name label does not cause the pool to reapply its template. Normal pool reconciliation is not assumed to continually restore a conflicting name. API-conflict retries remain bounded and respect current ownership; suppressed or ambiguous repairs remain visibly unresolved and outside the automatic convergence guarantee. These are naming-service compatibility requirements with unchanged lifecycle backends.

### Naming-service deployment and ownership

**Proposed packaging: a dedicated HCO-managed naming service.** At inspected HCO revision [`7ecd1cb`](https://github.com/kubevirt/hyperconverged-cluster-operator/commit/7ecd1cbc75775ba9579e54854db2026957eec7cc), HCO [manages supporting webhook operands](https://github.com/kubevirt/hyperconverged-cluster-operator/blob/7ecd1cbc75775ba9579e54854db2026957eec7cc/controllers/operandhandler/operandHandler.go#L59-L67) and could deploy the naming service's Deployment, Service, settlement/status resources, validation webhook, RBAC, and certificates. HCO configures, health-checks, and upgrades those resources and defines disablement and uninstall. The customer policy source of truth is the HyperConverged CR, with `v1` and supported `v1beta1` configuration and upgrade behavior defined before release. Neither a separately installed operator nor a new repository is required; code location is an implementation choice. The service observes persisted VM UIDs, settles assignments, repairs eligible new-VM conflicts outside GitOps management, validates known explicit edit/clear conflicts, checks pool membership read-only before repair, and publishes status and GitOps conflict signals without changing Git-owned labels. Its webhook has **no precreate reservation side effect**. Keep validation availability separate from HCO's inspected [single-replica webhook Deployment](https://github.com/kubevirt/hyperconverged-cluster-operator/blob/7ecd1cbc75775ba9579e54854db2026957eec7cc/deploy/operator.yaml#L132-L145) unless that deployment receives an availability redesign. The naming webhook runs alongside KubeVirt's existing [VM validating webhook](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virt-operator/resource/generate/components/webhooks.go). Supported-version tests verify naming-service compatibility with unchanged pool, clone, and restore controllers.

The earlier strict-uniqueness prototype created a claim during admission. [Admission does not guarantee persistence](https://kubernetes.io/docs/reference/access-authn-authz/extensible-admission-controllers/#side-effects): on OpenShift Virtualization 4.22.12, a later KubeVirt validation rejection left an unbound claim; a corrected retry could bind after a prototype change, but a retry-pinned name could remain reserved indefinitely. Twenty overlapping creates persisted one VM in another test, yet that did not prove safe claim release. This VEP now chooses post-persistence settlement, so direct `oc create vm` needs no precreate claim or completion signal. These tests remain evidence for **why strict admission-time claims were not selected**, not evidence that the new controller algorithm works. GitOps uses its source manifest and conflict remediation without a separate naming request; ordinary direct creation remains supported.

API machinery and KubeVirt reviewers should examine the new settlement and validation race model: whether VM watch/list handoff, UID-bound assignment records, conditional repair, and eventual status reporting can meet the desired convergence objective without KubeVirt code changes. If the product later requires strict uniqueness **at API success**, it must reopen the direct-create completion and claim-release design; merely moving admission between HCO and KubeVirt does not supply an outcome signal. An upstream API-machinery dependency would then be possible, not assumed for this eventual model.

Kubernetes [ResourceQuota issue #25484](https://github.com/kubernetes/kubernetes/issues/25484) recorded quota usage increasing during admission even when later validation rejected object creation. Its specific validation case was fixed, but maintainers discussed the broader need for quota/storage atomicity and the absence of a post-storage outcome hook. The open [cross-resource ValidatingAdmissionPolicy request #133631](https://github.com/kubernetes/kubernetes/issues/133631) explicitly names uniqueness against other resources as a use case. A cross-resource read, even if added, would not serialize concurrent VM writes. These precedents explain why validation only rejects **known** edit conflicts in this design.

OpenShift [Route](https://github.com/openshift/api/blob/master/route/v1/types.go#L1355-L1372) demonstrates a related post-persistence contract: duplicate requested hosts can be stored, while the [router rejects a competing route for active host use](https://github.com/openshift/router/blob/main/pkg/router/controller/unique_host.go#L1135-L1175) and reports admission status. VM display names differ because the naming service suffixes eligible losing new VMs outside GitOps management, preserves Git-owned labels with conflict alerts, and allows mutable edits. The comparison supports explicit requested-versus-assigned status, but does not prove this VM design or its convergence time.

The earlier strict-claim prototype exercised diskless and storage-backed VMClone/VMRestore on one release, including explicit new-target restore naming and a sequential storage-backed clone. It predates the current label and post-persistence design and does not prove its behavior. Current compatibility tests must run the existing APIs unchanged, observe resulting VM events, and verify naming-service repair/status or GitOps conflict alerts. No lifecycle admission mutator, new completion-status field, or callback to the naming service is required. Optional prompts and naming-state presentation belong to the UI.

Two packaging alternatives are:

1. **KubeVirt-owned naming.** `virt-api` could validate edits and a KubeVirt controller could settle names, making the policy available to standalone KubeVirt. This requires `kubevirt/kubevirt` changes, upstream lifecycle gating, and a different ownership and release plan. It is not selected in this VEP; clone, restore, and pool-controller changes are outside the proposed delivery scope.
2. **Webhook and controller in HCO's existing binaries.** HCO could validate edits from its webhook binary and reconcile assignments in its manager. This avoids a dedicated service Deployment but couples naming availability and scale to HCO's binaries. Its current single-replica webhook deployment would need an availability redesign. It does not by itself solve pool, clone, restore, or GitOps integration.

[VEP-190 structured plugins](../190-kubevirt-structured-plugins/vep.md#admission-policies-and-webhooks) are another possible **registration wrapper**, not a replacement for the naming service. A `Plugin` can reference admission webhooks, but VEP-190 assigns their deployment and deletion to another component. Its launcher and node hooks act on VM runtime lifecycle rather than reconciling persisted VM metadata across a namespace. At inspected KubeVirt revision [`bf19f733`](https://github.com/kubevirt/kubevirt/blob/bf19f7334a2fe318f8c1e654880c8844d0265ff3/staging/src/kubevirt.io/api/plugin/v1alpha1/types.go), the admission-reference fields exist but `PluginStatus` is empty and no runtime consumer of those references was found outside API/generated code; the `Plugins` gate is [Alpha](https://github.com/kubevirt/kubevirt/blob/bf19f7334a2fe318f8c1e654880c8844d0265ff3/pkg/virt-config/featuregate/active.go). Requiring a `Plugin` now would add a KubeVirt gate and version dependency without providing settlement, suffix assignment, status, or pool integration. HCO should deploy the webhook and controller directly. Plugin registration can be reconsidered if it gains relevant readiness/lifecycle support on the supported release matrix.

The naming service, status/settlement storage, and validation must be ready before `AutoResolve` reports active. The validation webhook must have no claim side effect, and its failure behavior must distinguish naming edits from unrelated/status updates. HCO must specify whether creates fail closed while settlement is unavailable or are accepted as visibly unresolved; it cannot promise prompt repair while the service is down. Shutdown and uninstall must not leave an orphaned fail-closed webhook or falsely report settled status. HCO-managed deployment, RBAC, certificates, high availability, readiness, bounded reconciliation lag, and recovery are initial-delivery requirements. Admission-serving replicas must remain available through rolling upgrades if edit validation is fail-closed.

### Feature gate and policy controls

The label uses existing VM metadata and needs no new VM spec field or schema generation. The naming service handles observed lifecycle metadata propagation; clone, restore, and pool controllers gain no naming behavior. The [KubeVirt feature lifecycle policy](../../../docs/feature-lifecycle.md#can-a-vep-choose-to-not-include-a-feature-gate) expects a VEP to justify omitting a KubeVirt gate. Under the proposed scope, behavior is implemented in the HCO-managed naming service and lifecycle availability is managed by HCO; KubeVirt binaries gain no behavior to gate under this scope. The display-name metric label is companion observability-controller behavior and reads existing metadata independently of the HCO naming gate; any collector rollout control belongs to that component, not a new KubeVirt gate. HCO's [feature-gate configuration](https://github.com/kubevirt/hyperconverged-cluster-operator/blob/main/docs/cluster-configuration.md#featuregates) therefore provides the proposed lifecycle control for the naming service (provisional gate name `vmDisplayName`, subject to HCO review). This is an HCO-owned gate, not a gate propagated to the KubeVirt CR. At Alpha it is off until explicitly enabled; at Beta it is on by default after activation; at GA the HCO lifecycle gate is removed. **Whenever the HCO gate is active, `AutoResolve` is the namespace policy default**, subject to visible activation-pending status on existing deployments. `Disabled` is the explicit customer opt-out, not the lifecycle gate's off state, and `Warn` is an activation transition rather than an ordinary default. HCO must define the policy and gate consistently in `v1` and supported `v1beta1` APIs and ensure clients can observe gate and activation state.

HCO gate-off or rollback leaves label data untouched: no defaulting, stripping, or backfill. Existing readers can still render stored text safely, and native label edits and selector queries remain available. The UI reports that managed naming is unavailable; documentation explains that label edits and queries provide no managed conflict validation, repair, or settlement while the service is inactive. Ordinary canonical-name VM operations continue. HCO must not claim `AutoResolve` status in that state. Re-enabling requires a new conflict and pool scan because intervening writes may have introduced collisions; legacy duplicates remain activation-pending until resolved or explicitly opted out. A customer who wants the supported display-name workflow without repair uses `Disabled` instead of turning off the lifecycle gate. Standalone KubeVirt has neither this HCO gate nor the managed guarantee.

KubeVirt community review is still needed for the key, contract, and HCO-only scope of this VEP. A printer column for a label is separate work: verify JSONPath quoting for the slash-containing key and table-parser compatibility before proposing one. Console, naming service, HCO, observability-controller, and CLI documentation work each need owners and trackers for initial delivery. No production component is delivered by this document edit.

| `spec.displayName` with selectable fields | Requires VM API/schema changes and spec-generation/lifecycle work. Exact field selection depends on supported CRD selectable fields; uniqueness still requires coordination or post-persistence repair. |
| Separate VMInfo resource | Adds API, controller, RBAC, and synchronization work. |
| Literal object rename | Remains a separate, unresolved RFE with dependent-resource identity implications. |

Native `oc get vm -l kubevirt.io/display-name=sap-db` provides inventory selection. Action support must be checked per command and release: the inspected [`virtctl stop` implementation](https://github.com/kubevirt/kubevirt/blob/c418f32d6fefd864f19d3a7f436dd6bfa8827036/pkg/virtctl/vm/stop.go) requires one positional VM and does not register `-l`. Customers therefore discover candidates with `oc`/`kubectl`, select a canonical target, and pass its resource name and namespace to `virtctl`; this requires no new CLI implementation.

## Scalability

Native exact display-name queries use label selectors over populated values. Resource-name lookup and combined search retain their separate canonical-name path; no effective-name fallback query is required for display-name lookup. Optional label storage adds no blanket writes or backfill; conflict repair writes only an eligible new VM's label outside GitOps management. GitOps conflicts add status and alert signals without label writes. Default `AutoResolve` adds a UID-bound settlement/status record per VM, validation for affected edits, and reconciliation on VM events. A metadata edit produces a normal VM update/watch event. Occasional CLI lookup can list and filter without a persistent full-object cache; metadata-only LIST still returns ObjectMeta and can still be large. Console watchers already load resources and apply filters before local pagination on inspected paths, but authorization scope, fetch limits, and incomplete pages must be measured before claiming complete search. Bound suggestions and fetch complete filtered results through a proven path. Benchmark label-filtered queries alongside combined resource-name/display-label search, namespace- and cluster-scoped discovery, and metadata-only list/watch at representative fleet sizes, including large inventories; measure update frequency and response size. Do not add a search backend without evidence.

Measure settlement/status writes, validation latency, time from conflicting VM persistence to repair, and scale and availability during recovery after outages. Define an automatic repair objective and a visible degraded state, and measure GitOps conflict detection and alert latency separately from customer remediation time. Bound transition reporting and conflict-metric cardinality; alerts and metrics require reviewed ownership, rules, and runbooks.

The `display_name` label adds no fan-out to the current VM inventory, but changes to the effective name can increase retained historical series. Benchmark label size, rename churn, scrape cost, and remote-write impact. Avoid copying mutable display text onto all runtime metrics.

## Update/Rollback Compatibility

Existing and older VMs have no key and still display their resource name. Direct VM create and direct label edits remain usable under active HCO `AutoResolve`, subject to known-conflict validation and later repair/rollback outside GitOps management. GitOps labels remain unchanged by the naming service; persisted conflicts require alerts and source correction. A full-object replace can remove a label it does not preserve; merge patch or server-side apply of the chosen key avoids clobbering unrelated metadata but does not bypass validation. Managed-field ownership, GitOps drift, and older clients need tests. Supported readers must handle empty and unexpected values during mixed-version rollout. Disablement of any future UI integration does not erase stored labels.

Default policy activation on existing deployments cannot silently rewrite legacy collisions or retroactively reject every existing VM. The transition reports conflicts and lets administrators resolve them or explicitly opt out. The service must establish UID-bound settlement for conflict-free legacy VMs, hand off its inventory to a continuing watch, and remain visibly pending while unresolved legacy conflicts remain; it need not provide a strict scan/write fence because new races are provisional and automatically repaired where eligible or reported for GitOps source remediation. Upgrades, policy disablement, and operator removal must specify status, validation, and recovery behavior. A label edit alone does not alter the VM spec. Supported runtime flows and selector dependencies must meet the lifecycle contract; pool, clone, restore, import, and backup integrations must be checked by supported release. Literal name-based policies remain unaffected and may still require the original full-rename RFE.

Observability-controller upgrades add `display_name`; older exporters and rollback versions omit it. Dashboards and other consumers must handle both schemas and retain canonical queries. Metric-source migration must select one authoritative source or explicitly deduplicate across sources using canonical identity. The display-name feature does not depend on adding the label to the legacy `virt-controller` exporter.

Kubernetes audit records follow the configured [audit policy](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/); this proposal cannot promise old and new names at every audit level. If an implementation needs Events, it must specify emitter, retry, deduplication, and success criteria; Events are not a durable history.

## Functional Testing Approach

Product implementation work, not this VEP edit, needs coverage for:

- Absent, set, change, clear, and explicitly empty labels; fallback, no blanket backfill, and conflict-only repair writes; label syntax, the 63-character boundary, accepted uppercase/dot/underscore values, rejected spaces/Unicode/slashes, long resource-name fallbacks, and safe text rendering.
- Name-only edits to running/stopped VMs during ordinary operation and live migration, with no naming-induced VMI, guest, network, or storage change.
- Observability-controller `kubevirt_vm_info` label values for absent, empty, set, changed, cleared, suffixed, and rolled-back VM labels; label punctuation and long resource-name fallback; top-level versus template placement; one current sample per VM; rename series turnover, canonical joins/counts, alert identity and duration, time-window queries, mixed exporter versions, and scrape-source migration.
- UI case-insensitive subsequence search over canonical names and nonempty display labels, complete authorized result scope, bounded autocomplete, native CLI identity output and explicit resource-name versus label-selector lookup. Verify UI zero/one/many selection and documented CLI result inspection, including allowed cross-mode matches.
- Label population through CLI, GitOps manifests, and UI forms; existing GitOps VMs gain their label through a source change and sync, retain it through subsequent syncs, and become discoverable by its stored value without changing canonical identity. Exact display-name queries match populated values only, with absent/empty keys excluded. Resource-name lookup and combined search still find unlabeled VMs and long canonical names. Test clear/removal, canonical/display cross-mode matches, case-distinct values, namespace RBAC, and canonical result deduplication.
- Unchanged Clone/Restore APIs and controllers producing VM events; inherited labels, new-target suffixing, in-place target UID/label handling, and snapshots made before display-name support. Verify naming-service status independently of lifecycle completion; optional UI prompts cannot be required for raw API success.
- VM pool creation, scale-out, template updates, and rollout with absent or static display labels; child fallback names, template updates that overwrite repairs, preservation of pool revision labels, stable repair after the update, existing-pool activation, and supported-version behavior. Verify that display-name-only repair does not cause template reapplication.
- Naming-service read-only checks of VM pool ownership `matchLabels` and every `matchExpressions` operator; unsafe/ambiguous membership suppresses repair and raises actionable status without rejecting pool API writes or changing ownership. Activation scans and UI guidance cover existing uses. No unintended VMI/Pod or policy effects on rename, suffix, or clear.
- Import mapping of spaces, Unicode, unsupported punctuation, and overlength source names to user-approved valid values; different sources mapping to one base, collision repair, and final assigned-name reporting.
- Default `AutoResolve`, explicit `Disabled`, visible activation-pending/`Warn`, explicit and fallback collisions, allowed display-name/resource-name cross-mode equality, case-sensitive equality, and provisional versus settled lookup.
- HCO Alpha gate-off, Beta gate-on, and GA gate-removal behavior; stored labels and canonical VM operations across gate transitions; conflict detection before reactivation after gate-off writes.
- Parallel direct creates and racing edits/clears; deterministic winner, ordered `-1`/`-2`/`-3` candidates, occupied-candidate skipping and concurrent candidate collisions, stable UID-bound assignments without renumbering after deletion, candidate reuse by new VMs, last-settled rollback, 63-character suffix construction and prefix truncation including decimal digit growth, same-VM retries, resource-version conflicts, tampering, delete/recreate, other-webhook rejection, dry-run, and dependency outage/recovery.
- HCO installation of the dedicated naming service, certificate/RBAC and settlement/status readiness before activation; validation and reconciliation availability during replica or leader changes and rolling upgrades; HyperConverged `v1`/`v1beta1` configuration and supported KubeVirt version skew.
- GitOps ownership declared before initial reconciliation, with set/absent/empty labels; direct create, adoption, ownership removal, namespace-policy changes, and clone/restore/import classification. Prove zero naming-service label writes, including queued suffix/rollback retries and adoption races; preserve unrelated Git-owned labels.
- GitOps/GitOps and mixed-ownership collisions on explicit and fallback names; preserve existing settled holders, report all canonical identities, and avoid renaming an unrelated VM. Known conflicting edits reject with sync errors; raced edits/clears alert without rollback. Nonconflicting Git corrections from `Conflict` settle and release obsolete assignments.
- Conflict metric and warning-alert firing, deduplication, workload namespace and canonical identity, persistence across repeated syncs/restarts, clearing after verified remediation/deletion/disablement, stale/missing data and availability alerts, and dry-run limitations.
- Lifecycle updates that overwrite/remove a recorded repair: trusted classification, stable safe reassignment, GitOps adoption races, and explicit user edits on controller-owned VMs. Test no naming-induced lifecycle rejection, no repeated suffix allocation, bounded API-conflict retries, conflict alerts, and stable settlement after a pool template update without display-name-induced template reapplication.
- Clone/restore storage preparation followed by provisional VM creation, independent naming repair/status and UI readback; backup/disaster-recovery settlement rebuilding using existing controller behavior.
- Upgrade, policy disablement, webhook/service upgrade and uninstall with visible degraded status, no unbounded repair loop, and no permanent write lockout.

Benchmark discovery and settlement operations separately, including repair latency at scale. Tests must establish the actual release-specific clone/restore behavior rather than assuming all API versions apply patches to existing targets.
