## Overview
This VEP proposes enhancing KubeVirt's cloud-init metadata support by enabling users to add custom metadata to cloud-init behind the Alpha `CloudInitDataExtensions` feature gate.
It adds `metaData` and `metaDataSecretRef` to NoCloud and ConfigDrive, and supports flat and nested values.

## Motivation
KubeVirt's cloud-init support previously did not allow users to add custom values to the metadata. 
This prevented users from passing application-specific information to their VMs through cloud-init.
Issue https://github.com/kubevirt/kubevirt/issues/15836 the motivation behind this VEP.

## Goals
- Enable users to add custom metadata fields to cloud-init through the metaData field in both `NoCloud` and `ConfigDrive` configurations
- Implement `MetaData` in the `CloudInitNoCloudSource` and `CloudInitConfigDriveSource` struct to allow users add custom metadata to the cloud-init
- Implement `MetaDataSecretRef` in the `CloudInitNoCloudSource` and `CloudInitConfigDriveSource` struct to allow users to reference Kubernetes secrets containing custom metadata
- Ensure custom metadata is properly merged with standard metadata fields (instance-id, local-hostname, instance-type, etc.) that KubeVirt automatically generates
- Use the `CloudInitDataExtensions` gate shared with [VEP #455](https://github.com/kubevirt/enhancements/pull/463)
- Implement upper limits on the number of metadata entries (32 top-level keys), payload size (2 KiB inline / 32 KiB in a Secret) to prevent resource exhaustion

## Definition of Users
VM owners and workload developers who need to pass custom metadata to their virtual machines 
through cloud-init for application configuration, environment-specific settings, or runtime parameters. 
This includes developers deploying applications that require custom configuration data accessible via cloud-init metadata,
such as environment variables, application settings, or deployment-specific parameters.

## User Stories
- As a VM owner, I want to add custom metadata fields to my cloud-init configuration 
so that my applications can access application-specific configuration data.
- As a VM owner, I want to reference Kubernetes secrets containing
custom metadata so that I can securely pass sensitive configuration data to my VMs.

## Design
Enhance `CloudInitNoCloudSource` and `CloudInitConfigDriveSource` with `MetaData` field as `map[string]interface{}` and `MetaDataSecretRef` for secret references. If a user defines a top-level key that KubeVirt also sets, KubeVirt's generated value takes precedence.

### Feature gate

`CloudInitDataExtensions` is an Alpha gate, disabled by default, and is shared with [VEP #455](https://github.com/kubevirt/enhancements/pull/463).
Admission rejects these fields while the gate is disabled.

### Entry Limits and Validation
To protect cluster resources and prevent abuse, the following limits will be enforced:

- **Key limit**: Maximum number of custom top-level metadata entries (keys) is **32**
- **Payload limit**: Inline metadata is limited to **2 KiB**; Secret data is limited to **32 KiB**
- **Depth limit**: Nesting depth is limited to **8**, counting the root object as depth 1
- **Enforcement**: Limits are enforced during API validation, preventing VMI creation if metadata exceeds the thresholds
- **Limit scope**: Limits apply to the combined count of:
  - All key-value pairs in the `metaData` map
  - All key-value pairs from the referenced secret in `metaDataSecretRef`
  - Standard metadata fields generated by KubeVirt are not counted toward the limit

This approach provides resource protection while allowing users flexibility within reasonable bounds.

## API Examples
```yaml
volumes:
- name: cloudinitdisk
  cloudInitNoCloud:
    userData: |
      #cloud-config
      package_update: true
    metaData:
      app_name: "my-application"
      environment: "production"
      cost_center:
        id: "12345"
        location: "Brno"
```

```yaml
volumes:
- name: cloudinitdisk
  cloudInitNoCloud:
    userData: |
      #cloud-config
      package_update: true
    metaDataSecretRef:
      name: my-metadata-secret
---
apiVersion: v1
kind: Secret
metadata:
  name: my-metadata-secret
type: Opaque
stringData:
  metaData: |
    app_name: "my-application"
    environment: "production"
    cost_center:
          id: "12345"
          location: "Brno"
```

## Scalability
- **Metadata entry limits**: A maximum of 32 top-level keys for custom metadata prevents resource exhaustion from excessively large metadata payloads
- **Payload limits**: Inline metadata is limited to **2 KiB**; Secret data is limited to **32 KiB**
- **API validation**: Limits are enforced during API validation, preventing VMI creation if metadata exceeds the thresholds
- **Performance impact**: The 32 top-level key limit with payload limit ensures cloud-init processing remains performant and does not impact VM startup times
- **Resource protection**: Limits protect against both accidental misconfiguration and intentional abuse of the metadata feature

## Update/Rollback Compatibility
- New field is optional; existing VMIs remain unaffected.
- Disabling the gate blocks new VMIs that use these fields but leaves running VMIs unchanged.
- On downgrade, projected volumes fall back to errors or no-op.
## Functional Testing Approach
- Unit tests: API validation, struct marshaling, metadata merging.
- Integration tests: Deploy VM/VMI with custom metadata, verify metadata is accessible in guest.
